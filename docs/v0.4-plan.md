# mast-web v0.4.0 plan

**Status:** draft, 2026-08-20 (post-v0.3.0, `cc33330`). Sequenced roadmap for v0.4.0 — retires the classic shell in favour of `solo` and `spatial`, reconciles the state seam those two grew around, revises the chrome, ties the authenticated human to the sessions they own, and puts the container image on a real cluster. Companion to [`web-design.md`](./web-design.md) (the architecture, evergreen) and [`shells-design.md`](./shells-design.md) (which this plan partly amends — see §1). Rots when v0.4.0 tags out.

## Goal

Ship **mast-web v0.4.0** with:

1. **`index.html` retired.** ✅ **Landed, PR 4 (#61).** `solo.html` and `spatial.html` are the product; the classic console went away rather than becoming shell #1. Sixteen of the classic shell's `client.*` capabilities had to exist somewhere else first — §2 is the inventory, and that inventory is also the answer to "what data and APIs do we need", which is why it went first. `index.html` keeps its *name* as a 37-line chooser (`web/shell-select.js`), because a static host serving the tarball has no Go server to rewrite `/` with.
2. **A state seam that both surviving shells actually use.** ✅ **Landed, PR 1 (#58).** At plan time `web/state/` was loaded by `index.html` alone, so retiring the classic shell would have deleted the only consumer of the v0.3.0 PR 1 refactor while `agents.js` carried a second, smaller copy of the same idea. The stores are factories now and every terminal holds its own pair; #61 removed the last singleton instances, which existed only for `app.js`. §3.
3. **Chrome and theme revision.** Ten themes ship and the room-lighting contract landed with the spatial shell; what is left is the HUD, the sidebar, and a status bar that is not one. §4.
4. **Session ownership, visible in the browser.** core-agent already stamps an ACL `Owner` from the caller and filters `GET /sessions` per identity — and the real-backend rig already proves it over HTTP. No shell shows any of it. §5.
5. **A real cluster deployment.** We ship a multi-arch distroless image and have zero Kubernetes artifacts. Kind in CI first; GKE behind it. §6.

Non-goals for v0.4.0:

- **A chat shell** (`shells-design.md` §5, S3). Three surfaces is already the thing this release is trying to reduce. Revisit once §1 and §3 have collapsed the count to two.
- **A fleet dashboard** (`shells-design.md` §6, S4). Depends on the same seam, and on unread-watermark design that has not been done.
- **A framework or build step** (`web-design.md` open question 3, `shells-design.md` S2). Still owed an explicit argument, and v0.4 makes the codebase *smaller*, which is the wrong moment to answer it. Carried forward, deliberately, with the note that it has now been deferred twice.
- **`--auth-mode=oidc`.** Blocked on purser phase 1a shipping `authn/oidc`; see §5 and §7. The flag stays a hard error rather than a half-implementation.
- **Per-turn caller attribution** (`shells-design.md` §9). Still the right protocol ask, still upstream's to ship, still not on this release's critical path now that chat is out of scope.
- **ACL mutation / session sharing.** core-agent has no route for it (§5). If we want "share this session with bob", that is a core-agent design pass, not a mast-web feature.

## Design overview

### 1. Two shells, not three — and what that does to `shells-design.md`

`shells-design.md` (2026-08-16) proposed a shell registry with today's console extracted as `shells/console/` (S1), and the spatial prototype landing beside it as `shells/spatial/` (S5). Reality since diverged in two ways worth naming rather than quietly working around:

- **The new shells landed as separate documents, not as registered shells.** `spatial.html` and `solo.html` are full HTML entry points with their own script lists. There is no `shells/registry.js`, no `?shell=` selector, no `mast-web:shell` key. The seam S1 called for was never cut.
- **The console is now slated for retirement, not extraction.** That is a change of decision, not a change of plan: S1's whole purpose was to prove the seam by lifting the console out cleanly. If the console is going away, the forcing function goes with it.

So v0.4 amends the phasing rather than executing it. What survives from that doc: the layering rule (`attach-core` → `state` → presentation), the shell contract's *discipline* even without a registry, the §7 division of labour with switchboard, and the §9 protocol ask. What does not: S1 as written, and S5's framing of spatial as a fork to land.

The selection mechanism the user flagged as TBD:

| Input | Precedence | Notes |
|---|---|---|
| `?shell=solo` / `?shell=spatial` | 1 | Deep links and smoke specs. Same shape `shells-design.md` §4 proposed. |
| `localStorage['mast-web:shell']` | 2 | Operator preference, set from the HUD. |
| Default | 3 | **Proposal: `solo`.** It is the surface that works on a laptop trackpad, in a narrow window, and for someone who has never orbited a 3D room. `spatial` is the one you choose. |

**Decided (2026-08-21): two documents.** `solo.html` and `spatial.html` stay separate entry points. A `/` that mounts a shell per `shells-design.md`'s registry is architecturally cleaner, but it is new structure in the release whose point is to remove structure — it is deferred alongside the framework question (§ Open questions 3), and re-evaluated against the post-retirement line count rather than this one. The precedence table above works over two documents unchanged.

### 2. The capability inventory — what retiring `index.html` actually costs

Measured at `cc33330`, distinct `client.*` methods called per shell:

| Shell | Public `AttachClient` methods used |
|---|---|
| `app.js` (classic, 4363 LOC) | 16 |
| `spatial.js` + `solo.js` + `terminal.js` + `agents.js` (3799 LOC) | 7 |

The seven shared: `connect`, `disconnect`, `listSessions`, `autoSelectSession`, `selectSession`'s sibling `createSession`, `inject`, `interrupt`.

**The nine unported, which are the retirement bill:**

| Method | Surface it backs | Notes |
|---|---|---|
| ~~`whoami`~~ | "signed in as X" | **Landed, PR 2 (#59).** Fetched in the background on the capabilities frame, stored as `session.whoami`, rendered into a HUD slot in both shells and by `/whoami`. Also the §5 dependency. |
| ~~`getUsage`~~ | cost / context meters | **Landed, PR 2 (#59).** `/usage` prints session totals plus the per-model split; the snapshot also repairs totals for a client that attached mid-session. |
| ~~`listTools`~~ | `/tools` | **Landed, PR 2 (#59)**, in the grouped-by-source shape core-tui#289 arrived at rather than the flat one app.js had. Renderer is shared (`SlashRender.renderTools`), so both shells agree. |
| ~~`listConfiguredSubagents`~~ | `/subagents` | **Landed, PR 2 (#59).** |
| ~~`getSubagentEvents`~~ | subagent drill-down | **Landed, PR 2 (#59)** as `/subagents events <name> [since]`. The app-qualified path is resolved from `GET /sessions` on demand — a terminal is built from a session id alone and has no sidebar to read it off. |
| ~~`getGuardrails` / `resetGuardrails`~~ | `/guardrails [reset]` | **Landed, PR 3a (#60).** Gated on `features.guardrails`; a 409 renders as the refusal it is, and a successful reset also clears the cost-ceiling input freeze. |
| ~~`deleteSession`~~ | session delete from the sidebar | **Landed, PR 3b (#60).** A hover-revealed `×` on each session row, behind a `confirm()` that names the session by title. The registry action resolves `{ ok, error }` rather than throwing, and a refusal shows as a transient per-daemon notice — not `lastError`, which the sidebar only paints when the record's state is `error`. The shell is told after the server agrees (`onDeleted`) and closes the tab or panel. |
| ~~`selectSession`~~ | explicit session switch | **Not ported, PR 3b (#60) — and this is the answer, not a deferral.** It exists to re-point one client at another session. Both surviving shells hold one `AttachClient` per tab or panel, so there is nothing to re-point: retargeting would leave the frame captioning a session it is no longer attached to. The gesture it backs — "switch to that session" — is `Mod+K`, a fuzzy session picker over every attached daemon, which opens or focuses. `/sessions` stays read-only for the same reason. |

`terminal.js`'s own header already writes this list down and calls it *unported, not excluded* — "a terminal in a panel should not be a lesser terminal than one in a tab". v0.4 makes that comment true or deletes it honestly; it does not get to stay aspirational through another release. **All nine are answered as of PR 3b — eight ported, `selectSession` answered by a better gesture — and the header comment is now a description of what shipped rather than a list of what is missing.**

Two of these are shell-level rather than terminal-level (`deleteSession`, `selectSession`): they act on the roster, not on a turn. `deleteSession` became a sidebar gesture; `selectSession` turned out to belong nowhere in a shell that gives every panel its own client, and the gesture it stood for became `Mod+K`. The rest are per-session and belong in `terminal.js` or in a drawer it owns.

Also unported and not an `AttachClient` method: the classic shell's **client-side slash commands**. PR 3a took the per-session half — `/mcp`, `/specialists`, `/sessions`, `/model`, `/guardrails`, `/export`, `/clear` — and **closed #45** along the way: `terminal.js`'s built-ins are a table of descriptors, and `/help` filters it with the same `available()` call dispatch checks, so a command cannot be listed and then refuse. Absent `features` map, or absent key within it, still reads as on (§2.1, additive). PR 3b took the shell-level half — `/attach`, `/theme`, `/layout`, `/batch`, `/shortcuts`, the batch runner, the keyboard-shortcuts overlay, the command palette and the session picker — into a new `web/shell.js` (`MastShell`), plus the sidebar's delete gesture.

The seam matters more than the list. A shell hands its commands to `MastTerminal.create({ commands })` as the same descriptor shape the built-ins use, and they join the same table: `/help` lists them under a "This shell:" heading, `available()` gates them, and the command palette reads `terminal.commands` rather than keeping a list of its own. That is #45 one level up — a palette that offers a name the prompt would refuse is the second read all over again. A shell cannot shadow a built-in; `/clear` means the same thing in every panel of every shell.

`/endpoint` was **not** ported. It opened the classic shell's setup modal to swap the one backend; these shells have an attach form in the sidebar and hold several backends at once, so the command has nothing to do. `/attach` adds one and says so.

`/stats` was **not** ported. It printed the same numbers `/usage` already prints, from the locally accumulated total rather than the authoritative `GET /usage` — and it had been throwing since the `byModel` alignment, because the renderer read three fields (`totalToolCalls`, `avgTtfbMs`, `avgTotalMs`) that `getStats()` deliberately stopped returning. Two commands for one answer, one of them broken, is not a thing to carry forward.

#### What the deletion itself turned up (PR 4, #61)

The inventory above counted `AttachClient` methods and slash commands. Reading `index.html` line by line before deleting it found four things that were neither — sentences and states the classic shell painted into chrome that the new shells have no equivalent of. All four were ported in #61 rather than lost:

| What | Where it went |
|---|---|
| The **observer banner**. The classic shell said "attached as observer; this agent runs autonomously" when `capabilities` withheld write. The new shells had the read-only gating but not the sentence — an operator typed into a prompt that silently refused. | `ui.observerBanner` in `terminal.js`, pinned to the top of the transcript rather than appended as a system row (appending means it scrolls away around the time someone starts wondering why nothing responds). `/clear` re-paints it. `.term-observer` is sticky in `spatial.css`. |
| The **observer usage backfill**. A client that attaches to a running session has no `last_turn` of its own; the classic shell seeded the footer from `getUsage()`. | Same call, in `case 'capabilities'`, guarded to observer sessions. |
| **`capabilities.agent`** — the agent's name, version, model and provider (protocol §2.1). The classic shell painted it into an `#agent-info` sidebar slot. A terminal has no sidebar slot. | Reported by **`/model`**, which is the question it belongs to: the model is the agent's, not the session's. Dropping it was the alternative, and it is the one field that answers "what am I actually talking to". |
| The **expired-session diagnostic**. A 401 from `GET /config` is the one discovery failure that names its own fix; the setup modal said "your session with this server expired — reload the page". | A **sticky** notice on every registered row in `daemon-sidebar.js`. `setNotice` auto-expires after 8s, which is the wrong vehicle for a condition that does not stop being true while you look at it, so it grew a `sticky` argument. |

Deliberately **not** carried over: the setup modal itself (`/attach` and the sidebar form replace it, and `/endpoint` was already answered above); its token-input hiding behaviour, which existed because that modal was the only way to enter a token; `index.html`'s boot banner, which announced a page that no longer exists; and the classic sidebar chrome (`.server-item`, `#backend-info`, `#identity-info`, the model `<select>`) — all of it either superseded by the daemon sidebar or by a HUD slot that already shows the same fact.

**No new backend API is required by this item.** Every method above already exists on `AttachClient` and is exercised by `client.test.js`. That is the useful conclusion from doing the inventory first: the answer to "what data/APIs do we need" is *the ones we already have, wired into the shells that survive*.

### 3. The state seam

`index.html` loads `state/subscriptions.js`, `state/session.js`, `state/connection.js`, `state/daemons.js`. **`spatial.html` and `solo.html` load none of them.**

This was deliberate — `spatial.html`'s own comment says "No state/ stores and no app.js — the spatial shell keeps its state per terminal instead of in a set of singletons" — and the reasoning was sound at the time: the v0.3.0 stores were written as singletons for a one-terminal shell, and a room of four terminals cannot use a singleton session store. But the consequence is now load-bearing:

- `web/agents.js` (341 LOC) is a second daemon registry alongside `state/daemons.js` (148 LOC). Both hold `AttachClient` instances per endpoint, both read `mast-web:daemons`, and only one of them survives §1.
- Per-terminal state lives in closures inside `terminal.js`, so nothing outside a terminal can observe it. That is exactly the constraint that blocks a status bar showing real status (§4), cross-session unread, and a fleet view later.

The fix is not "make the new shells load the old stores" — it is **de-singleton `state/session.js` and `state/connection.js` into per-session instances**, then have `terminal.js` own an instance rather than a closure, and fold `agents.js` into `state/daemons.js`. That is the same de-singletoning `shells-design.md` S5 observed `terminal.js` had already done informally; this makes it the shared version.

Behaviour-preserving, and it is the prerequisite for §4 and §5 both.

### 4. Chrome and themes

The theme work is further along than the tracking suggested. Landed with #49 and #46: ten themes (`web/theme.js`), the Google/Aurora palettes, the `--room-*` / `--panel-shadow` / `--hue-1…4` lighting contract, and the shared light-room block that fixed `paper` and `solarized-light` floating light panels in a black void. `spatial.css` has no hardcoded near-blacks left.

What is actually outstanding:

**a. The status bar is not one.** ✅ **Done, PR 5 (#62).** It was seven hardcoded keyboard hints and a clock in the room, three and a clock in solo. `web/status-bar.js` is the replacement, shared by both shells. What it reports is deliberately not what a terminal's own status line reports — every panel already carries its conn dot, model, turn count, cost and elapsed timer at the foot of its own transcript, and repeating one of those would be a second read of the same number for the price of a whole bar. So it answers the window-level questions a panel cannot: agents attached and how many are down, terminals open and how many are mid-turn, **the summed cost**, and which terminal is in front with its connection state. The sum is the one that matters — a room of six sessions has six cost figures and no total. It polls nothing: it subscribes per terminal through PR 1's seam, which is the thing that seam's own comment said it was for, and the shells only report the two facts no store emits (the set of terminals changed; focus moved). The dropped hints were a third copy — both shells list their keys in the sidebar hint and `/shortcuts` lists all of them. The open-terminal count also came out of the HUD in both shells and landed in the bar, where it can say how many of them are busy.

**b. Solo reuses spatial's IDs.** ✅ **Done, PR 5 (#62) — split, not accepted.** This was open question 2 and it is resolved in favour of the split. A selector census showed solo was reaching into ~1360 of `spatial.css`'s 1907 lines, so one shared sheet was not enough: the cut is three ways. `chrome.css` (702) is the furniture both shells wear — HUD, status bar, sidebar, atmosphere overlays, batch drawer. `panel.css` (1007) is a terminal — bezel, screen, boot flash, damage states. `spatial.css` (538) is what is left once you take a terminal and its frame out of the room: camera, grid planes, floor casts, radar. `solo.css` (309) stopped being an override layer and became what it says it is. `#spatial-hud` / `#spatial-sidebar` / `#spatial-status` are `#app-*`; the room-only ids (`#hud-camera`, `#hud-radar`, `#btn-audio`, `#btn-tile`, `#btn-reset`) kept their names. The split was proved lossless rather than eyeballed — a top-level selector census over the original sheet versus the three new ones, diffed as multisets, leaving exactly four intentional discrepancies. No selector is defined in two sheets, which is what makes the load order safe to reason about.

**c. `styles.css` is 2645 lines and shared by all three.** ✅ **Done, PR 4 (#61): 2658 → 1739 lines.** A meaningful fraction was classic-shell chrome that died with `index.html` — the sidebar, the input area, the status bar, the HUD strip, the boot banner, the collapsibles, the `#output-area` scrollbar. It was deleted rather than left; a shared stylesheet that nothing shares is how dead CSS becomes permanent. The prune was scripted off a per-rule audit (every id/class in a selector checked against `id=`/`class=` attributes in the surviving HTML and string literals in the surviving JS, comments stripped so prose could not keep a dead selector alive), and re-run afterwards to confirm zero fully-dead rules remain. Two custom properties went with the rules that used them (`--sidebar-w`, `--accent-hover`). What stayed is the transcript vocabulary, the modals and palette, the layout modes, the batch panel (`shell.js` builds it), and `@keyframes cursor-blink` — which both shells animate and neither could own alone. The command palette and batch table were on the original list to delete and are **not** dead: PR 3b moved both into `shell.js`.

**d. Two theme registries.** ✅ **Done, PR 4 (#61).** `web/theme.js` lists ten themes for the new shells; `app.js:2973` had its own `THEMES` const for `/theme`. The duplication existed because `index.html` was frozen and could not gain a `<script>` tag. That constraint died with §1, and the duplicate went with it — adding a theme is now two edits, a palette block and a list entry.

**e. The HUD/sidebar colour revision** the user asked for. ✅ **Done, PR 5 (#62)**, after (a) and (b) as planned. The audit found one problem in several places: `--accent` was the resting colour of every HUD button, the sidebar's section heading, the selected session, the hover tint on an unselected one, the audio toggle's "on", the terminal in front, a turn in flight, and the clock. A strip where eight controls are lit cannot say which one matters. The rule is now that `--accent` means *this one is live* — selected, in front, mid-turn, switched on, under the pointer — and everything that was accent for decoration is `--text`. Two pairs were ambiguous rather than merely loud, both a state and a pointer in the same hue four percent apart: session hover (12%) against selected (16%), and button hover (14%) against pressed (16%). Hover is a neutral `--text` tint in both now, and the pressed rule generalised out of `spatial.css` into `.hud-btn[aria-pressed='true']`. The demotion raises contrast in all ten themes, because `--accent` is a hue and `--text` is the one colour a palette must make readable: against `--bg-surface`, solarized-light 3.00 → 4.39, cloud-light 3.51 → 15.89, solarized-dark 3.53 → 4.86, pantheon-light 4.51 → 16.10, paper 6.26 → 12.23, grayscale-dark 9.52 → 14.29, none the other way. No theme variables were touched; #46/#49 did that and it holds.

Two loose threads were folded in while the sheets were open. `#batch-panel` had its insides in `styles.css` and an outer-frame override in `chrome.css`, because the base rule was still shaped for the classic shell — a flex child of the document, with `border-top` under the transcript — so the two rules disagreed about what the element was. With that shell gone there is nothing to disagree with: the frame folded into the base rule and the whole block moved to `chrome.css`. And `styles.css`'s `.status-item { display: flex }`, the classic status bar's, stranded by PR 4 and inherited by accident when the new bar took the class name over, is deleted.

### 5. Session ownership in the browser

**The daemon side is already built.** Verified against `core-agent` at time of writing:

- `POST /sessions` stamps the ACL `Owner` from the caller's identity (`pkg/attach/handlers_create_session.go:43`).
- `pkg/auth/authorize.go:76` defines `SessionACL{Owner, Viewers, Contributors}` with a documented action matrix: Read = Owner/Viewers/Contributors, Write = Owner/Contributors, Admin = Owner, plus a global `Admin` bypass.
- `GET /sessions` filters per caller — `reg.ListAuthorized(c)` for live sessions and `store.ListVisibleTo(c)` for evicted/idle ones (`pkg/attach/handlers.go:377-430`) — explicitly so the list does not leak other operators' activity patterns.
- ACLs persist across restart (`pkg/attach/session_acl_store.go`), and `mast` carries the same `pkg/auth` and `pkg/attach` code.
- Enforcement is gated on `attach.multi_session.enabled` (`pkg/attach/server.go:360`).

**And our own rig already proves it end to end.** `dev/tools/e2e-real-backend` sets `multi_session.enabled: true`, provisions alice/bob/`sa:mast-web`, and section 5 asserts "alice sees her session" / "bob does not" through the BFF. Identity forwarding, header scrubbing and the CSRF guard are all covered too.

**So the gap is entirely ours, and it is entirely in the browser.** Not one of `spatial.js`, `solo.js`, `terminal.js`, `agents.js` contains the string `whoami`, `caller_id`, or `identity`. The shells cannot say who you are, cannot say whose session you are looking at, and there is no Playwright coverage of a multi-user deployment at all — the mock is single-identity.

v0.4 scope, in the order it should land:

1. **Show the caller.** `whoami()` on connect, `capabilities.caller_id` as the fast path, rendered in the HUD. Falls out of §2's `whoami` port.
2. **Show the owner.** Session rows carry an owner; "mine" versus "shared with me" is a sidebar distinction, not a new API — the filtered list plus `whoami` is enough to derive it.
3. **Create owned sessions deliberately.** `agents.js:188` already calls `createSession()`. Make the ownership consequence visible instead of incidental.
4. **Multi-user smoke.** Teach the mock a second identity and an ACL-filtered `/sessions`, then assert in a browser what the rig asserts over curl. This is the coverage that stops a future refactor from silently showing bob alice's sessions. Overlaps **#42** (align mock fixtures with the real wire shape).
5. **Adopt purser where it is ready.** See §7 — `authn/bearer` and the `Caller` contract are stable; `authn/oidc` and `authz/` are not.

Explicitly out: sharing/ACL mutation (no route upstream), and `--auth-mode=oidc` (blocked, §7).

### 6. Kind, then GKE

We have a working multi-arch distroless image (`Dockerfile`, `ghcr.io/go-steer/mast-web`, `$BUILDPLATFORM` cross-compile) and **zero Kubernetes artifacts** — no manifests, no chart, no kustomize, and nothing k8s-shaped across the five workflows (`ci.yml`, `ci-docs.yml`, `docs.yml`, `release.yml`, `smoke.yml`). The image is tested by `docker run`, never by a scheduler.

**Kind first, as a CI target** (the user's answer: "I think CI but let's see as we go"):

- `deploy/k8s/` — Deployment, Service, ConfigMap, and the health probes the server already serves (`/healthz`, `/readyz` are the entire anonymous surface since #55).
- A `kind.yml` workflow: build the image, `kind load docker-image`, apply, wait for ready, then assert `/readyz` is 200 anonymous **and** `/config` is 401 anonymous. That last assertion is the one worth having — it is the deployment-shaped version of what #55 landed, and it is the check that catches an ingress accidentally exempting a path.
- **Decided (2026-08-21): `--mode=mock` in PR 7, with the real-backend upgrade filed as a follow-up.** The two load-bearing assertions do not need a real agent behind them, and a core-agent image plus its config and lifecycle would push PR 7 off the day-one parallel track. The workflow must say in its own comments that it is not real-backend coverage — an unqualified green Kind job reads as more than it is. [#66](https://github.com/go-steer/mast-web/issues/66) is what stops "mock for now" from becoming permanent by default — unmilestoned, to be picked up when the Kind job has proven itself or when a real-backend deployment bug gets past the mock, whichever comes first.

**GKE after**, and deliberately not in this release's critical path: it needs an issuer, IAP, and a Workload Identity story, which means it wants §5.5 and purser's OIDC work to have landed. Writing the manifests so the GKE delta is an overlay rather than a rewrite is the v0.4 obligation; standing up the cluster is not.

Also unblocks **#6** (hosted SPA to GitHub Pages) by forcing the question of which artifact is the deployable one — and **#7** (flip the repo public) is worth sequencing against whatever the cluster work exposes.

### 7. purser

`~/projects/purser` — "shared authentication and authorization for go-steer services: caller identity from SPIFFE X.509-SVIDs, standard-CA client certificates, and OIDC tokens."

**Status: phase 1a, in progress.** Shipped: the `Caller` / `AuthSource` contract with context plumbing (stdlib-only), `authn/bearer`, `authn/mtls` (`NewPKI` + `NewSPIFFE`, matched-pair constructors returning a `*tls.Config` alongside the Authenticator), and `authtest.RunAuthenticatorSuite` as a conformance harness. **Not shipped, and named in the README as next: `authn/oidc`, the authorization layer, the HTTP middleware, and the client helpers** — with the explicit warning that "nothing here is importable as a stable API until phase 1a is complete."

Those four are precisely what mast-web would import. So the honest v0.4 position is:

- **`authn/oidc` is the blocker for `--auth-mode=oidc`.** The mode constant exists (`cmd/mast-web-server/auth.go:59`) and `main.go:249` hard-errors on it. Keep the error until there is a real implementation to point at. Its planned shape — issuer discovery, JWKS with caching and rotation, audience/expiry validation, claim→identity mapping defaulting to `email` and falling back to `sub`, remaining claims into `Caller.Labels` — is a superset of what our `iap-jwt` path does by hand, so this is a replacement, not an addition.
- **`authz/rules.go` is the blocker for anything past exact-match identity lists.** Its planned ordered-rule model replaces core-agent's `AdminIdentities` / `ProxyIdentities` exact-match config (`pkg/config/config.go:1095` / `:1113`). Our rig's `proxy_identities: ["sa:mast-web"]` is exactly the degenerate case that stays valid.
- **Two things we can do now, cheaply.** (a) **mast-web is missing from purser's consumers table** — core-agent, mast, core-tui, switchboard and k8s-lookout are listed. A one-line PR there makes us a stakeholder in the phase-1a API shape rather than a late adopter of it. (b) Adopting `purser.Caller` as the internal identity type in `cmd/mast-web-server/auth.go` costs one dependency (purser's `go.mod` has a single require, `go-spiffe`) and makes the eventual OIDC swap a wiring change.

The tie-out the user asked for — authenticated human → the sessions they create and attach to — is therefore *already coherent across the three repos*. core-agent and mast implement it, the BFF asserts identity into it, and purser is the future common implementation of the identity half. mast-web's job in v0.4 is to participate and to make it visible.

Sensible order to ship:

1. PR 1 (foundation — everything visible depends on it)
2. PR 0, PR 7 and PR 8 in parallel from the start (touch no shell code)
3. PR 2, then PR 3a, then PR 3b
4. PR 4 (the retirement; wants 2 and 3 finished so nothing is lost)
5. PR 5 and PR 6 (both want PR 1; PR 5 also wants the CSS prune from PR 4)

PR 4 is the one to be disciplined about: it should be a deletion, reviewed as a deletion, with the capability port already merged and demonstrated. Retiring the classic shell in the same PR that ports its features is how features get lost quietly.
