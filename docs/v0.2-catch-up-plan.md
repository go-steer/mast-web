# mast-web v0.2.0: catch-up plan

**Status:** draft, 2026-07-16. Sequenced roadmap to bring mast-web to feature parity with `coretuiremote` (the Go adapter powering `core-agent-tui`) in browser form, while establishing the architectural seams required for mast-web to eventually serve `mast` (which will advertise different capabilities and a different slash-command surface than core-agent). Companion to [`upstream-drift-2026-07-16.md`](./upstream-drift-2026-07-16.md) (what drifted) and [`web-design.md`](./web-design.md) (the architecture — will be updated in Phase 4). Rots when v0.2.0 tags out.

---

## Goal

Ship **mast-web v0.2.0** with:
1. **Wire-protocol parity** — clean consumption of SSE spec v1.2.0 (no missed fields, no wrong event names).
2. **Feature parity with coretuiremote** — the browser can do everything the terminal can do, translated to the browser idiom.
3. **Backend-agnostic UI** — no hardcoded slash commands, no hardcoded sidebar sections. The UI reads what the server advertises via `capabilities` + a `/slash-catalog` endpoint (to be added server-side) and adapts. When mast ships with a different capability set, mast-web works against it without a code change.
4. **Shared conformance harness** — one set of JSON fixtures both `mast-web`'s `attach-core` and `core-agent`'s `coretuiremote` pass. Catches wire-protocol drift the moment it happens, in either direction.

Non-goals for v0.2.0:
- Phase D features that depend on unshipped backend work (plan-first plan-rendering, watchdog alerts, cost-ceiling reset). Design-visible but implementation-blocked.
- A shared Go/JS/TS *library* (option 3 as originally framed). We deliberately downshift to a shared *spec* — cheaper, no build pipeline, no language interop, same alignment guarantee.
- AG-UI protocol support. Attach-only for v0.2.0; AG-UI is a v0.3.0+ topic once mast ships.

## Design overview

### The three layers mast-web splits into

Today `web/app.js` (1317 LOC) is a single file that mixes wire-protocol parsing, UI state, and DOM rendering. That's the biggest single obstacle to option 3. Split into:

```
web/
├── attach-core/          # wire layer — no DOM, no globals, tested in isolation
│   ├── protocol.js       # SSE event parsing, hyphenated typed events, capability frame
│   ├── errors.js         # PermanentStreamError classification (404/401/403 → terminal)
│   ├── replay.js         # connectedAt - replayGrace cutoff
│   └── client.js         # SSE connection + HTTP helpers + peer fan-out
├── state/                # observable state model — one source of truth for rendering
│   ├── session.js        # per-session state (usage, tools, agents, memory, skills, mcp)
│   ├── connection.js     # connection state machine (idle/connecting/live/degraded/terminal)
│   └── capabilities.js   # what the current backend advertises + slash catalog
├── app.js                # rendering + interaction only — subscribes to state/
└── index.html + styles.css
```

Rules:
- `attach-core/*` never touches the DOM. It emits typed events; `state/*` reduces them; `app.js` subscribes to state changes and paints.
- `attach-core/*` and `state/*` are testable in Node without a browser (via `vitest`) — this is what the conformance harness runs against.
- Rendering never reads directly from the SSE stream — always from `state/*`. Prevents the "stale event painted into new session" class of bug that core-tui solved with the session-generation counter (which becomes trivial to enforce in a reducer).

### Shared conformance spec (option 3, pragmatic form)

We do NOT build a shared client library. We build a shared **conformance fixture set** that lives in a canonical location (proposal: `core-tui/docs/conformance/`, alongside the existing SSE protocol spec doc). Each fixture is a pair:

```
conformance/
├── streams/
│   ├── 001-happy-turn.jsonl                    # raw SSE frames
│   ├── 002-cost-ceiling-mid-turn.jsonl
│   ├── 003-idle-eviction-during-attach.jsonl
│   ├── 004-permanent-401-mid-stream.jsonl
│   ├── 005-observer-mode-usage-update-only.jsonl
│   └── ...
└── expectations/
    ├── 001-happy-turn.json                     # expected client state after each frame
    ├── 002-cost-ceiling-mid-turn.json
    └── ...
```

Both `mast-web/attach-core` (JS) and `core-agent/internal/coretuiremote` (Go) run their protocol layer against the same fixtures and verify the observed state matches the expectation JSON. Divergence = one of the two got the protocol wrong. Same discipline coretuiremote already has for its own tests, extended so the two consumers are held to the same standard.

Cost: ~2 days to build the harness runner in JS + Go; each fixture is ~15 min to author. Fixture authoring is a one-time front-load then incremental. Coretuiremote's existing test cases are the seed inventory.

Ownership: `core-tui/docs/conformance/` (spec-adjacent). Any protocol change lands with a new fixture PR against core-tui; both consumers pick it up on their next cycle.

**Why not a shared library:** language interop cost (JS/Go), build pipeline for JS bundling, versioning coordination across three repos, forced-lockstep upgrade cadence. The conformance-spec approach lets both consumers evolve independently at the *implementation* level while staying pinned to the same *behavior* — and it's cheap enough to actually happen.

### Capability-driven UI (the mast-compatibility seam)

Today mast-web hardcodes slash commands (`app.js` slash dispatch), sidebar section presence, agent identity, and model-list availability. When mast ships with a different set of slash commands (say `/orchestrate`, `/federate`, `/pause-until`) and no `/mcp` sidebar (because mast's MCP model differs), a hardcoded UI breaks or shows dead controls.

The fix is server-driven advertisement, all consolidated on the `capabilities` first-frame. Spec bumps to v1.4.0 (v1.3.0 was consumed 2026-07-17 by the digest-savings sidecar).

**`capabilities` frame gains four fields** (server-populated, all optional, all forward-compat):

1. **`capabilities.features: {…}`** — feature-flag map: `{multi_session, perms_stream, cost_ceiling, observer_mode, mcp, specialists, cross_daemon, interrupt, federation, …}`. Sidebar sections and UI affordances key off this. Unknown flags tolerated silently.

2. **`capabilities.slash_commands: [name, …]`** — dynamic list of available slash commands, populated server-side by probing capability interfaces (e.g. `CompactSlashProvider` presence → `"compact"` in the list). No new endpoint, no registry refactor. Client renders known names via a static metadata table (signature, summary, help text); unknown names render generically ("no help available — server-advertised"). Adding a new command server-side makes it *discoverable and functional*; adding rich help text is a client change but doesn't gate the command working.

3. **`capabilities.agent: {name, version, description, model, provider, url}`** — the agent's own identity. Consolidates what's scattered across `/.well-known/agent-card.json`, `GET /sessions/{app}/{sid}/status`, and the existing `capabilities.server` string. Browser renders the header: *"Connected to `<agent name>` (`<model>`) at `<url>`"*. When mast ships, it advertises `{name: "mast", …}` — the UI displays it correctly without a code change.

4. **`capabilities.caller_id: "alice@example.com"`** — display hint for who the operator is authenticated as. Just the string, so the browser can paint "Signed in as X" without a second round trip. Backed by a real `GET /whoami` endpoint (`{identity, admin, source ∈ {bearer, mtls, iap, asserted}}`) for auth debugging and non-browser consumers.

**Dynamic capability changes** ride an optional `capabilities` field on `status-update` (merge semantics — absent = unchanged). Handles cases like an MCP server registering mid-session or a permission mode flipping.

**Rule for v0.2.0:** every sidebar section, every slash command, every identity render MUST be conditional on advertised capability. No hardcoded list; no `if (backend === 'mast')` branch anywhere. Client-side commands that don't talk to the backend (`/help`, `/endpoint`, `/theme`) stay hardcoded — they're SPA-owned, not server-owned — but they're merged with the server-advertised set at render time.

### Slash-response renderer dispatch (the "don't paint into a corner" seam)

Related but distinct concern: today every server slash returns a hardcoded response DTO (`CompactResponse`, `CheckpointResponse`, `ReplanResponse`). Rendering is per-command in the client. Adding a new command that returns structured data (a plan tree, a search-result table) means writing bespoke rendering. This is a long-standing gap shared with coretuiremote.

Full solution — schema-driven response rendering with a renderer registry, client-side schema validation, table/tree/chart primitives — is a v0.3.0+ chunk. What we build now is the **dispatch skeleton** so extending it later isn't a refactor:

- Tiny client-side dispatcher that routes slash-response JSON through one of N built-in renderers (v0.2.0: `text`, `markdown`, `json`). Default to `json` when no hint.
- Reserved response-body conventions: `_render: "text"|"markdown"|"json"|<future>` and `_schema: <ref>` as optional top-level keys the server can include. Nothing consumes `_schema` in v0.2.0 — the naming convention is what we lock in.

Cost: ~50 LOC of JS + a scope note in the spec that these keys are reserved. Bought: adding a new server command with a text/markdown/JSON return works out of the box; adding one that returns structured data is a renderer-registry entry, not a rewrite.

## Roadmap

Four weeks. Each week is one focused PR-set; issues bundle by phase, not by day.

### Phase 1 (week 1) — Protocol bootstrap + attach-core extraction

**Blocking work.** Nothing else lands cleanly until protocol is right and the split has happened.

- **Issue A** — Align attach client with SSE v1.2.0.
- **Issue B** — Extract `attach-core/` and `state/` modules from `app.js`. No behavior change; enables per-module tests.
- **Issue C** — Wire-protocol conformance harness (shared JSON fixtures + runner in JS; Go runner is a parallel PR against core-agent).

Exit criteria: `/stats` shows real per-model breakdown; per-turn cost has cache attribution; tool-result rows show real latency; hitting a 404 SSE reconnect stops retrying and shows a terminal banner; `vitest` runs conformance fixtures green.

### Phase 2 (week 2) — Session lifecycle + un-stub sidebar

Everything in the sidebar today either works but stubs data, or throws on interaction.

- **Issue D** — Real session create / delete / switch (`POST /sessions`, `DELETE /sessions/{app}/{sid}`, guard the `default` session, session generation counter, atomic sidebar refresh on switch per bug #274).
- **Issue E** — Un-stub sidebar features: real `/stats` from `usage-update.by_model`, real `/model` switching via server model list, `/clear` distinguishes DOM-clear from `DELETE`, `/export` semantics, identity endpoint. (Some sub-tasks are server-side — see open questions.)
- **Issue F** — Replay-cutoff filter (`connectedAt - replayGrace`) so attaching to a long-running session doesn't dump full history into the chat.

Exit criteria: "+ New" creates a real backend session; row-delete removes it; switching between sessions produces the correct sidebar state atomically; reconnecting to a live session shows only fresh events.

### Phase 3 (week 3) — Feature parity with coretuiremote

- **Issue G** — `/interrupt` button (soft-cancel current turn) + observer-mode `/interrupt` support (per #304).
- **Issue H** — `/perms/stream` bridge with reconnect (5s→30s backoff, 501-means-give-up, ctx-cancel-safe decision send). Mirrors `coretuiremote/prompter.go`.
- **Issue I** — Observer mode (`LiveAgent` equivalent): single long-lived subscription, `StampLatestAssistantFooter`-style patching on `turn-complete` + `usage-update.last_turn`, capability-aware observer banner text.
- **Issue J** — Cross-daemon `/attach <url> [<sid>]` + peer fan-out via `GET /peers` (parallel, per-peer 5s budget).

Exit criteria: a browser session can interrupt turns, respond to permission prompts, attach as observer to a long-running session with correct per-turn footer, and switch to a peer daemon via `/attach`.

### Phase 4 (week 4) — Capability-driven UI + docs reconcile

The seam that makes mast-web mast-ready.

- **Issue K** — Capability manifest + identity: consume `capabilities.{features, slash_commands, agent, caller_id}` from the first frame + optional `status-update` hot changes; gate every sidebar section, every slash command, and both identity slots on server-advertised data. Consumes core-agent's v1.4.0 spec bump (sibling PR).
- **Issue L** — Slash-response renderer dispatch: tiny client-side dispatcher (`_render: text|markdown|json`); reserve `_render` and `_schema` response-body key conventions. Doesn't build the renderer registry (v0.3.0+); establishes the seam so adding one isn't a refactor.
- **Issue M** — Docs reconcile: apply the §8.1 checklist from [`upstream-drift-2026-07-16.md`](./upstream-drift-2026-07-16.md) — swap mast URLs, bump protocol version to v1.3.0, flip Phase C★ status to Shipped, fix event names. Delete `upstream-drift-2026-07-16.md` after this lands (its rot condition).

Exit criteria: mast-web renders correctly against a synthetic backend that advertises a stripped-down or expanded capability set (including unknown slash commands rendered generically); a slash response with `_render: "markdown"` renders through the markdown pipeline; docs no longer reference deleted `core-agent/docs/mast/*` URLs; changelog entry for v0.2.0.

## Design decisions (resolved 2026-07-16)

These were the cross-repo open questions; all resolved during design review. Recorded here for provenance; scope reflected in Issues K/L and the sibling core-agent PRs listed at the end.

1. **Advertisement shape.** `capabilities` first-frame gains four new fields (`features`, `slash_commands`, `agent`, `caller_id`). Dynamic changes ride an optional `capabilities` field on `status-update` (merge semantics). Spec bumps to v1.4.0 (v1.3.0 was consumed 2026-07-17 by the digest-savings sidecar). Rationale: one round trip on connect; aligned with version negotiation; `status-update` merge handles hot changes without a second connection.
2. **Slash discovery.** Dropped the `GET /slash-catalog` endpoint idea. Instead, `capabilities.slash_commands: [name, …]` populated server-side by probing capability-interface presence. Rich metadata (signature, summary, help text) stays client-side as a static table keyed by name; unknown names render generically. Rationale: no core-agent registry refactor; graceful degradation for future divergent commands (mast ships `/federate`, mast-web renders it functional with generic help immediately, rich help follows in the next release). Renderer dispatch skeleton (Issue L) preserves the seam for structured-return commands without paying the full schema-driven rendering cost now.
3. **`/export` semantics.** Client-side JSON export of the rendered transcript for v0.2.0. Server-side JSONL of the raw eventlog is deferred — operators wanting the canonical audit trail should use whatever tooling reads `pkg/audit/` directly, not a mast-web-specific path.
4. **Identity — two surfaces.**
    - **Agent identity:** `capabilities.agent = {name, version, description, model, provider, url}`. Consolidates what's currently scattered across `/.well-known/agent-card.json`, `GET /status`, and the existing `capabilities.server` string.
    - **Caller identity:** `GET /whoami` endpoint for the standard curl-friendly whoami pattern; `capabilities.caller_id` display hint on the frame so the browser paints "Signed in as X" without a second round trip on connect. **Shipped response shape (core-agent#344):** `{identity, admin, source, proxy_by}` where `source ∈ {bearer, mtls, iap, asserted, anonymous}` and `proxy_by` is set when auth was delegated via `X-Asserted-Caller` (the proxy allowlist path). mast-web surfaces this as "alice via bot-service" when `proxy_by` is present.
5. **`/reset-ceiling`.** Deferred entirely. mast-web renders the cost-ceiling banner + "contact your admin" placeholder for v0.2.0. Spawn a design-only issue on core-agent to spec reset semantics (does reset bump the ceiling, restart it, wipe the accumulator?); revisit for v0.3.0.
6. **Conformance fixture location.** ~~`core-tui/docs/conformance/` — co-located with the SSE protocol spec doc.~~ **Revised 2026-07-20:** cross-repo shared test assets are annoying (vendor + sync tooling either way), and the friction outweighs the payoff for 5 fixture files with low churn. mast-web keeps fixtures at `web/attach-core/conformance/fixtures/`; core-agent#330's Go runner vendors a copy at `core-agent/internal/coretuiremote/conformance/fixtures/` (in practice: core-agent#344 landed fixtures at `pkg/attach/testdata/conformance/` in a per-frame `.json` format that also works for the Go-side runner). Revisit when a fixture-drift scenario actually bites; likely answer at that point is a shared `go-steer/attach-conformance` repo with a tiny sync script per consumer.

### Issue A — [Phase 1] Align attach-client with SSE v1.2.0

**Labels:** `phase-1-protocol`, `enhancement`

**Summary**

Our `web/attach-client.js` header claims spec v1.1.0. Real wire is v1.2.0 (per `core-tui/docs/sse-event-stream-protocol.md`, changelog 2026-07-16). We already use hyphenated event names correctly, but we miss several v1.1.1 / v1.2.0 fields and don't handle the terminal-error case. See [`docs/upstream-drift-2026-07-16.md`](../docs/upstream-drift-2026-07-16.md) §1 for the full delta.

**Scope**

- Parse `capabilities` first-frame; store `protocol_version` and `event_types`; gate feature detection off it (currently stored, never inspected).
- Read `usage-update.last_turn` sub-object as the authoritative per-turn cost source (with `tokens_in_cached` for cache attribution). Route per-turn footer through it, not `turn-complete.cost_usd` (which is now optional).
- Extract `latency_ms` from `tool-result.response` map (sidecar key, not top-level). Handle both `float64` (browser) and `int64` shapes. Surface in tool-call chip. Currently hardcodes 0.
- Handle `turn-error kind="cost_ceiling"`: persistent banner + disable input; recognize no matching `turn-complete` will follow.
- Coalesce `inbox` events on `dequeued` (dismiss "queued" toast).
- Classify reconnect failures via `PermanentStreamError` pattern: HTTP 404/401/403 → stop retrying + terminal banner; everything else → keep current backoff.
- Update file header to `spec v1.2.0`.

**Reference**

Port from `core-agent/internal/coretuiremote/typed_events.go` (translation shape) and `core-agent/internal/attachclient/status_error.go` (permanent-error classification).

**Exit criteria**

Per-turn cost shows cache attribution; tool rows show real latency; hitting a 404 on reconnect stops the loop and shows a terminal banner; `vitest` unit tests for each event type against fixtures land in the same PR.

### Issue B — [Phase 1] Extract `attach-core/` and `state/` modules from `app.js`

**Labels:** `phase-1-protocol`, `refactor`

**Summary**

`web/app.js` (1317 LOC) mixes wire-protocol parsing, UI state, and DOM rendering into one file. This blocks isolated testing, blocks the conformance harness, and makes the "stale-event painted into new session" bug class (which core-tui solved with a session-generation counter) hard to fix without cross-cutting changes.

**Scope**

Split into:
- `web/attach-core/` — protocol.js, errors.js, replay.js, client.js. No DOM access, no globals; imports only from itself and stdlib.
- `web/state/` — session.js, connection.js, capabilities.js. Observable state model; single source of truth for rendering. Reducer over typed events.
- `web/app.js` — rendering + interaction only. Subscribes to `state/*`; never reads from the SSE stream directly.

No behavior change in this PR. Rendering paths, slash commands, sidebar sections all stay functional. This is a scaffolding-only PR to enable Issue C + everything downstream.

**Exit criteria**

App loads and behaves identically to `main` pre-PR. New module boundaries have basic unit tests (event parse round-trip, state reducer invariants). No new features.

### Issue D — [Phase 2] Real session create / delete / switch

**Labels:** `phase-2-sessions`, `enhancement`

**Summary**

Today "+ New Session" calls `cmdClear()` (DOM-clear masquerading as create), row-click switches SSE but doesn't refresh sidebar sub-panels atomically (bug #274 lesson), and there's no session generation counter to drop stale events after a switch.

**Scope**

- "+ New" → `POST /sessions` (owned session, 201 → `{app, user, sessionID, url}`); on success, select the new row.
- Row-level delete button → `DELETE /sessions/{app}/{sid}`; refuse on the bootstrap `default` sid (server returns 403; UI guard prevents the request); optimistic UI + revert on failure.
- Session generation counter in `state/session.js`: every event carries the `sessionGen` captured at connection open; reducer drops events with mismatched gen. Ported concept from `coretuiremote/adapter.go` / core-tui's `agentcmd.go:229`.
- Switch-in-place atomic refresh: on session change, close current SSE, bump `sessionGen`, refresh `/usage`, `/memory`, `/skills`, `/mcp`, `/tools`, `/status`, and re-open SSE against the new sid — all before painting. Mirror `coretuiremote`'s `Brander` pattern.
- Idle/active badge in the sidebar row from `GET /sessions` `.status` field; sort rows by `last_touched_at` desc.

**Exit criteria**

Creating a session hits the backend; deleting removes it (except default); switching between two live sessions shows the correct usage + MCP list + memory for each with no cross-contamination; stale events from the outgoing session never paint.

### Issue F — [Phase 2] Replay-cutoff filter (don't dump full history on attach)

**Labels:** `phase-2-sessions`, `enhancement`

**Summary**

Attaching to a long-running session dumps the full eventlog into the chat pane, dwarfing recent activity. `coretuiremote/adapter.go:65-72,161,283-291` solves this with a `connectedAt - replayGrace` cutoff: replay everything up to `connectedAt - grace`, discard, then paint from grace onward.

**Scope**

- `web/attach-core/replay.js` — cutoff filter with a configurable `replayGrace` (default 30s, mirror coretuiremote).
- Wire into `state/session.js` reducer: events before the cutoff bypass the transcript panel but still update aggregate state (usage, tools).
- Optional "Load full history" affordance in the sidebar for the case where an operator explicitly wants scrollback.

**Exit criteria**

Attaching to a 1000-turn session shows the last ~30s of activity, not 1000 turns. Aggregate state (cost, tool counts) still reflects the full session.

### Issue K — [Phase 4] Capability manifest: dynamic UI + identity

**Labels:** `phase-4-mast-ready`, `enhancement`, `blocked-on-core-agent`

**Summary**

Enables mast-web to serve mast (with a different feature set, slash surface, and identity than core-agent) without code changes. All UI affordances key off the `capabilities` frame. No hardcoded backend-specific branches. Consolidates the four new fields agreed in the Q1/Q2/Q4 design decisions.

**Scope (mast-web side)**

- `state/capabilities.js` consumes four new fields from the `capabilities` first-frame:
  - **`features: {…}`** — feature-flag map gating: MCP sidebar section, Skills section, Specialists section, cost-ceiling banner, `/interrupt` button visibility, observer-mode banner text, per-model stats breakdown, cross-daemon session fan-out, federation (future). Unknown flags tolerated silently.
  - **`slash_commands: [name, …]`** — dynamic list of server-available slash commands. Merged with the client-owned local set (`/help`, `/endpoint`, `/theme`) for the autocomplete palette and `/help` output. Unknown names render with a generic entry ("no help available — server-advertised"); known names render from a static client metadata table (signature, summary, help text). Slash dispatch routes server-owned to `POST /slash/<name>`; client-owned to local handlers.
  - **`agent: {name, version, description, model, provider, url}`** — populates the "Connected to <agent> (<model>) at <url>" header slot. Replaces the hardcoded "Powered by attach protocol · core-agent / mast" string in `index.html:102`.
  - **`caller_id: "…"`** — populates the "Signed in as X" header slot. Display only; canonical identity comes from `GET /whoami` if the browser ever needs to re-verify.
- Consume optional `capabilities` field on `status-update` (merge semantics) for dynamic changes — e.g. an MCP server registering mid-session flips `features.mcp` true.
- v0.2.0 back-compat: if the manifest is absent (v1.2.0 server), assume all features true and use the hardcoded slash list.

**Scope (core-agent side, sibling PR)**

- Extend `capabilities` frame with the four new fields. Spec bump to v1.4.0 (shipped in core-agent#344).
- `features` populated from runtime state (MCP servers registered? SessionFactory available? cost ceiling configured? etc.).
- `slash_commands` populated by probing capability-interface presence (`CompactSlashProvider` → `"compact"`; `CheckpointSlashProvider` → `"done"`; etc.) — no registry refactor needed, just a small helper next to the existing hardcoded handler registrations in `handlers_operator.go:77-87`.
- `agent` populated from the same source that feeds `/.well-known/agent-card.json` and `GET /status` (model, provider).
- `caller_id` from the resolved `Caller.Identity` after auth middleware.
- Optional `capabilities` field on `status-update` for hot changes; not required in v0.2.0 unless there's a use case that drives it.
- Conformance fixture pair covering the new frame shape + a `status-update`-with-capabilities case.

**Also sibling core-agent side:** `GET /whoami` handler — `{identity, admin, source ∈ {bearer, mtls, iap, asserted}}`. ~15 LOC. Standard endpoint for auth debugging; unblocks non-browser consumers.

**Exit criteria**

Pointing mast-web at a synthetic backend that advertises `features.mcp: false, features.cost_ceiling: false` hides those sections without any client-side code change; advertising `slash_commands: ["compact", "federate"]` shows both in the palette (`/federate` generic-rendered); advertising `agent: {name: "mast"}` displays "Connected to mast" in the header. `curl /whoami` returns caller identity for auth debugging.

### Issue L — [Phase 4] Slash-response renderer dispatch + reserved conventions

**Labels:** `phase-4-mast-ready`, `enhancement`

**Summary**

Long-standing gap shared with coretuiremote: slash responses are hardcoded per-command DTOs; rendering is bespoke. Adding a command that returns structured data (a plan tree, a search-result table) requires bespoke client-side rendering. Full solution — schema-driven renderer registry, client-side schema validation, table/tree/chart primitives — is a v0.3.0+ chunk. This issue lays the dispatch skeleton so future extension isn't a refactor.

**Scope (mast-web side)**

- Client-side renderer dispatcher (`web/app/slash-render.js`, ~50 LOC): reads optional `_render` key on the slash-response JSON body; routes to one of the built-in renderers.
- Built-in renderers for v0.2.0:
  - `text` — plain string in a `<pre>` block
  - `markdown` — pass through the existing `marked` pipeline
  - `json` — pretty-printed JSON tree (default when `_render` absent)
- Reserved response-body key conventions, documented in `web/attach-core/protocol.js` header:
  - `_render: "text"|"markdown"|"json"` — chooses renderer
  - `_schema: <ref>` — reserved for v0.3.0 schema-driven rendering; ignored in v0.2.0

**Scope (spec side, small)**

- Note in `core-tui/docs/sse-event-stream-protocol.md` that `_render` and `_schema` are reserved response-body keys for slash-response JSON. Doesn't require a version bump — it's a client-convention doc addition.

**Not in scope (deferred to v0.3.0+)**

- Renderer registry as an extension point
- Table / tree / chart primitives
- Client-side schema validation
- Schema-driven input form generation for slash *arguments* (the analog problem)

**Exit criteria**

A hypothetical server slash returning `{_render: "markdown", body: "**Compaction summary:** …"}` renders as markdown in the browser without a mast-web code change. A response with no `_render` hint renders as pretty JSON. Reserved conventions documented in one place; renderer set is a table with three entries and a clear seam for adding a fourth.
