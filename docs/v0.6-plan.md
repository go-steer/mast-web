# mast-web v0.6.0 plan

**Status:** draft, 2026-10-06 (post-v0.5.0, `cfb77fc`). Supersedes [`v0.5-plan.md`](./v0.5-plan.md) (executed, v0.5.0 tagged 2026-10-06). Read against `core-agent@cfb1138` and `core-tui@f1bcdf7`.

## Goal

**mast-web consumes attach protocol 1.12.0. core-agent is on 1.19.0.** v0.5 closed a five-version gap; seven more versions opened in the nineteen days its tag waited, with nothing landing here in between. The v0.5 plan predicted exactly this and gave the instruction now being followed: don't extend the old plan, record the high-water mark and let the next release carry it.

v0.6 is that catch-up and nothing else. It is a narrow release on purpose. The hosting work that was going to be v0.6 ([#86](https://github.com/go-steer/mast-web/issues/86), [#66](https://github.com/go-steer/mast-web/issues/66), [#6](https://github.com/go-steer/mast-web/issues/6)) moves to v0.7. A catch-up that waits behind a feature release is how the interval grew in the first place.

The seven versions are not all additive in effect. **Two of them regress mast-web against a current daemon today**, in the released v0.5.0:

- **1.13.0 makes guardrail halts invisible, and probably makes a halted session a dead end.** A trip moved out of `turn-error` into its own `guardrail-trip` event, which this client drops. An operator gets a bare `canceled: turn canceled` where the explanation used to be, or nothing at all. Worse, see §2: by reading, an inject into a halted session leaves the composer stuck until reload. That is the same class of dead end 1.11.0 created for held sessions.
- **1.18.0 lets the permission card name a decision the daemon did not apply.** The card renders what was clicked, not what the daemon reports applying. That breaks the rule #94 was built on, "render the echo, not the request".

Both are in the v0.5.0 CHANGELOG's Known gaps. They lead this plan.

## Design overview

### 1. The drift, item by item

Sources: `core-agent/pkg/attach/events.go` (the per-version rationale, which ends at 1.19.0), `docs/site/src/content/docs/reference/attach-http.md` (the REST reference, which documents 1.13.0–1.19.0 more fully than anything else), and core-tui's [`sse-event-stream-protocol.md`](https://github.com/go-steer/core-tui/blob/main/docs/sse-event-stream-protocol.md), whose change log stops at 1.15.0. Where the three disagree, see the last paragraph of §2.

| Version | Change | What it costs us |
|---|---|---|
| **1.13.0** (#891) | Guardrail trips get a non-terminal `guardrail-trip` event `{guardrail, reason, halted_turn}`, and stop being reported as `turn-error`. A trip that cuts a turn is followed by a `canceled` turn-error that the producer no longer suppresses. | **Regression. §2.** |
| **1.14.0** (#1088) | `POST /perms/respond` answers **410** for a prompt whose turn ended before the answer arrived, where it used to answer 404. The two 410 bodies are different facts. | Small. §3. Our card prints any failure through `describeError`; it should say *the action was not taken* and which way it ended. |
| **1.15.0** (#1165) | A deny can carry a `reason`, which the model reads. Deny only; one line; ≤500 bytes after whitespace collapse; a 400 leaves the prompt pending. **A pre-1.15.0 daemon accepts the field and drops it**, so only `protocol_version` can tell you it reached the model. | Feature. §4. |
| **1.16.0** (#1168) | `POST /perms/mode` switches a running session's permission mode. SessionAdmin-gated, refusal is 404, **no frame announces the change**, and a change made mid-turn lands at turn end. | Feature. §4. |
| **1.17.0** (#1179) | On a multi-session daemon, `allow-always` from anyone but a daemon admin is applied as `allow-session`. The respond 200 gains `decision` and `downgraded`. | **Nothing directly.** We have never offered allow-always. But the `decision` field is the fix for 1.18.0 below, so it is consumed there. |
| **1.18.0** (#1175) | Auto mode. An escalated prompt carries `approver_model` / `approver_reason`; any allow on one is applied as allow-once (`downgraded: true`). `GET /perms` gains `settable_modes` and approval rows gain `approver_model`. `/perms/mode` accepts `auto`. Also `task_bytes` on inject (#1230). | **Regression on the card; feature elsewhere.** §3, §4. `task_bytes` costs nothing: it exists so a client that inlines `@`-file content can say where the operator's words end, and mast-web inlines nothing. Checked by grep, not assumed. |
| **1.19.0** (#1258) | Per-turn trips and every turn error become durable eventlog rows. They replay as content-less `agent` frames, and live clients receive each failure **twice** (typed frame + row), paired by a new `event_id`. | **Nothing breaks; an opportunity.** `fanoutAgentFrame` returns early on a frame with no `Content` (`protocol.js:54`), so the rows are silently dropped. No double rendering, but replayed history still shows turns that simply stop. §5. |

Two unversioned upstream changes are also in scope because they change what renders:

- **core-agent#1049**: a `cost_ceiling` trip against the *per-turn* bound ends its turn and nothing else; the session stays live. There is deliberately no `halted_session` field. `GET /guardrails` `halted` is the authority. This shapes §2.
- **core-agent#1154** ([#108](https://github.com/go-steer/mast-web/issues/108)): a subagent result can carry `output` *and* `run_error`, "delivered, with a warning". §6.

### 2. Guardrail trips, and the dead end behind them

**What a v0.5.0 operator sees against a 1.13.0+ daemon.** A watchdog or cost-ceiling trip mid-turn arrives as `guardrail-trip` (dropped: we do not know the name) followed by `turn-error {kind: "canceled"}`. The latter goes down the generic path at `terminal.js:1693` and prints `canceled: turn canceled`. The one sentence that says *why* the agent is about to refuse everything, and how to clear it, is the frame we threw away. A trip at a turn boundary prints nothing at all.

**The part that is worse than missing text, which is by reading and must be confirmed in PR 0.** Since core-agent#1040, an inject into a halted session is queued with a 200 and does not wake the agent, so no turn runs until a reset. Since 1.13.0, a turn refused because the session is halted emits no frame either. mast-web's `submit()` arms `setRunning(true)` and waits on a `runPrompt` promise that only a `turn-complete` or `turn-error` can settle. Neither is coming. So SEND stays disabled and STOP stays up until reload. STOP cannot help: `stop()` sends an interrupt for a turn that does not exist and never clears the running flag; only `submit()`'s `finally` does. That is 1.11.0's held-session dead end again, in a new place. PR 0 reproduces it against the mock before PR 1 fixes it, because a plan that fixes a bug nobody has watched happen is guessing.

**What PR 1 does.**

- **Render the trip verbatim.** `guardrail-trip` becomes a system block naming the guardrail with the producer's `reason` under it. Verbatim because the producer is the side that knows which reset clears what it tripped. The spec says consumers SHOULD NOT append advice, and core-tui deliberately shows no reset button for the same reason: an invented affordance is one release from naming a command that no longer exists.
- **Absorb the cancel it causes, exactly the way the spec says.** `halted_turn: true` arms a one-shot: the next turn-error, *if* it is `canceled`, renders nothing. The arming is spent on whatever turn-error comes next, cancel or not, so a rate-limit that follows still reaches the operator. It is also dropped at the turn boundary, so a trip cannot swallow the operator's own STOP on some later turn. `halted_turn` is read off the wire, never inferred from absence.
- **"Halted" comes from `GET /guardrails`, not from the trip.** Per core-agent#1049, a per-turn cost trip ends one turn and leaves the session running. A banner keyed off *any* trip would tell the operator to reset something that needs no reset. So a trip triggers a `/guardrails` read, and the read decides whether the session is halted. The 1.12.0 status poll already exists; it grows a guardrails read when the version is ≥1.13.0 and `features.guardrails` is on.
- **A halted session gets a banner and an honest composer**, built the same way as the hold banner (#70): the reason, the guardrail, and the way out. Typing at a halted session still sends, because upstream designed the inbox to queue for exactly this and the queue drives the first turn after reset. But it **does not arm the running state**, and it says so: *queued — runs after the guardrail is reset*. That is the dead-end fix. The window status bar gets a halted count beside the held count, for the same reason it got the held one: you cannot see a halted session from any tab but its own.
- **`/guardrail` is an alias for `/guardrails`.** core-agent's `reason` text says *"Clear it with /guardrail reset watchdog"*, which is core-tui's spelling. We render that text verbatim, so mast-web should answer to it. An alias is cheaper than an argument about whose spelling wins, and safer than rewriting producer text.
- **Pre-1.13.0 stays as it is.** Detection is `emitsEvent('guardrail-trip')`. A producer that does not advertise it still reports halts as `cost_ceiling` / `watchdog` turn-errors, and that path is kept as is.

**Where the sources disagree.** core-agent's events.go says `cost_ceiling` / `watchdog` "remain in the turn-error kind enum for the REFUSAL path". The spec and the REST reference both say a refused turn short-circuits *above* the emit site, so on a 1.13.0+ stream neither value appears as a frame. These are consistent: the enum values survive as returned errors and metric labels, not frames. 1.19.0 then writes a durable `turn-error` row for a refused turn, which reaches us as a content-less `agent` frame (§5). PR 0 should confirm against the producer which of these a 1.19.0 refusal emits, because the halted-composer behaviour above depends on whether anything ever answers a refused inject.

### 3. The permission card says what was applied

Three fixes to the card, all of the same kind as #94: show what the daemon says, never what we assumed.

- **The outcome is the reply's `decision`, not the click** (1.17.0 / 1.18.0). `resolvePermsRequest` writes the clicked decision into the card before the POST (`terminal.js:633`). That is good, because it gives immediate feedback and blocks a double send. It should be *replaced* by the reply's `decision` when one arrives, with `downgraded: true` shown as what it is: *applied as allow-once*. A pre-1.17.0 reply has no `decision`, and the clicked value stands, which is correct for a daemon that applied what it was sent.
- **An escalated prompt looks escalated** (1.18.0). When the frame carries `approver_model`, the card shows `approver_reason` **quoted and attributed to the model**. The reference is explicit that this is model output, steerable by arguments planted in the call, so it is never rendered as the daemon's own text. The card offers only **DENY** and **ALLOW ONCE**, since any wider allow is applied as once anyway. Offering ALLOW SESSION there would be offering something the daemon will not do.
- **A gone prompt says the action was not taken** (1.14.0). 410 is not an error to print verbatim. It is the answer to the one question a late approver has, and it has two bodies with two different next steps: *expired* (answer faster or raise `approval_timeout`) and *the turn ended first* (look at why the turn ended). 404 narrows to "already answered, or not this session's". Gated on 1.14.0, because before it a guardrail-cut prompt also answered 404 with a body that says "never issued".

`/perms` gets the matching read: an approval row with `approver_model` and no `by` reads *allowed by the approver model, `<model>`*. That extends #94's three-way attribution rule rather than breaking it, because `by` stays reserved for a verified human.

### 4. Two operator verbs on permissions

Both are features rather than repairs, and both are version-gated, because the daemon cannot tell us otherwise.

- **Deny with a reason** (1.15.0). A **DENY…** affordance beside DENY that asks for one line. It is offered only at ≥1.15.0, because an older daemon accepts the field and silently drops it, and an operator who typed a reason the model never saw has been lied to by the UI. Client-side we collapse whitespace and enforce the 500-byte limit before sending, so the 400 is a backstop rather than the UX. A 400 leaves the prompt pending, and the card must stay answerable rather than showing a decision that was not applied.
- **`/perms mode <mode>`** (1.16.0, `auto` from 1.18.0). It lives in the palette, for the reason `/share` does: it is SessionAdmin-gated and refused with 404, so only a panel, which knows the negotiated version, can tell "too old" from "not yours". With the version known, a 404 has one meaning, and the message says that one. `settable_modes` (1.18.0) is what we offer, in the order given, so the command never offers a mode it will be refused. Two upstream facts the output has to state rather than hide: **no frame announces a mode change**, so other clients and other tabs keep showing the old mode until they re-read `/perms`; and **a change made mid-turn lands when the turn ends**.

A clickable mode chip in the footer is deliberately not here; see §8.

### 5. Durable failures in history

1.19.0 is the version that makes §2 and §3 survive a reload. Each per-turn trip, each halt and each turn error now leaves a content-less eventlog row that replays as an `agent` frame:

| Row (`InvocationID`, `Author`) | What it is |
|---|---|
| `guardrail-trip`, `agent/guardrail-trip` | A trip that halted the session (exists since #643; gains `halted_turn` at 1.19.0) |
| `guardrail-turn-trip`, `agent/guardrail-turn-trip` | A trip that did not halt it |
| `gate-refusal-storm`, `gate/refusal-storm` | A refusal-storm cut (unchanged since #1081) |
| `turn-error`, `agent/turn-error` | Any turn error, **including a turn refused because the session is halted**, with `cut_by` when a guardrail caused it |

`fanoutAgentFrame` learns these four by **author and name together**, as upstream's own readers do, so a future row sharing an author cannot be misread. They render as the same blocks the live frames produce. The cancel-absorb rule from §2 applies on replay too, which is why the halt row now carries `halted_turn`. An older halt row without it reads as `false`.

**Live, every failure arrives twice**: the typed frame and the row. They pair on `event_id`, and the order differs by kind (a trip's frame goes first; a turn error's row goes first, behind the terminal barrier). So the rule is the spec's: **render whichever arrives first, drop the other**. That means a small seen-set keyed by event id, scoped to the session. `event_id` is absent when the session has no event log, and then there is nothing to pair and nothing to drop.

This is also where the walkthrough's v0.5 note about "a subagent that already finished" gets company: a replayed session should now read the same as a live one.

### 6. `run_error`: delivered, with a warning

[#108](https://github.com/go-steer/mast-web/issues/108) as filed, which matches core-tui#316 exactly: a tool result with a non-empty string `run_error` keeps its ✓ **Used** state and gains one warning line, `⚠ run failed after returning: <run_error>`. Keyed on the result key, never the tool name; `error` still wins; not version-gated, because it is a result-map key and an older daemon simply never sends it. **Not** a red ✗. That would tell the operator the result is junk, which is the misreading core-agent#1002 fixed for the model.

Unversioned and independent of everything above. It can land first if it is ready first.

### 7. What the mock owes

The mock declares `wireProtocolVersion = "1.12.0"` (`cmd/mast-web-server/mock.go:46`). v0.4's PR 0 set the discipline and v0.5 kept it: **bring the mock up to the version it claims, in the same PR that claims it.** For 1.19.0 that means:

- **Fixtures from the producer, not from this document.** Upstream ships `guardrail-trip-boundary-v1.13.0.json`, `guardrail-trip-cut-v1.19.0.json` and `turn-error-v1.19.0.json` in `core-agent/pkg/attach/testdata/conformance/`. Our new `.jsonl` fixtures (trip with cut, trip at boundary, durable rows with `event_id` in both orders) are derived from those. A shape test fails if they diverge, in the pattern of `TestMock_SessionRowsUseCanonicalWireShape`.
- **A guardrail the mock can trip on demand**, the way `POST /_mock/perms-prompt` raises a prompt: `POST /_mock/guardrail-trip {guardrail, halted_turn, halts_session}`. It sets `halted` in `GET /guardrails`, and an inject against a halted session is **queued and runs nothing**, which is the producer's behaviour since #1040 and the thing PR 0 exists to reproduce.
- **`/perms/respond` grows up**: the two 410 bodies (verbatim from `pkg/attach/prompter.go`), `decision` / `downgraded`, `reason` validation (deny only, 500 bytes after collapse, 400 leaves it pending), and an escalated prompt via the existing `/_mock/perms-prompt`, carrying `approver_model` / `approver_reason`.
- **`POST /perms/mode`** with the ACL's 404 for a non-owner, and `settable_modes` on `GET /perms`.
- **`/_mock/*` resets** for the new state (guardrails), added to the walkthrough's reset block.

### 8. What v0.6 is deliberately not

- **Hosting.** [#86](https://github.com/go-steer/mast-web/issues/86) (oidc), [#66](https://github.com/go-steer/mast-web/issues/66) (Kind against a real backend), and [#6](https://github.com/go-steer/mast-web/issues/6) (hosted SPA) are v0.7.
- **ALLOW ALWAYS on the card.** We have never offered it. 1.17.0 makes it admin-only on a multi-session daemon and silently downgrades it for everyone else, so adding it now would add a button whose most common outcome is a downgrade. If it ever comes, it comes with the `downgraded` rendering from §3 already in place.
- **A clickable permission-mode chip.** `/perms mode` is the verb. A chip is presentation over the same call, and because no frame announces a mode change, a chip that shows the mode would need its own polling story to stay honest. Not in a catch-up release.
- **[#106](https://github.com/go-steer/mast-web/issues/106)** (subagent count in the hold banner). Nothing in 1.13.0–1.19.0 gives the subagent roster liveness, so the gap it records is unchanged. Re-checked, not assumed.

## Sibling upstream (informational)

- **Attach protocol**: 1.19.0 as of `core-agent@cfb1138`. events.go's comment block is the per-version source; the REST reference in `docs/site/.../attach-http.md` is the clearest single read for 1.13.0–1.19.0.
- **core-tui's wire spec** stops at 1.15.0. 1.16.0–1.19.0 exist only in core-agent. That is worth knowing when the two disagree, and when citing.
- **core-tui#352**: core-tui does not yet show the 1.17.0 downgrade. After PR 2, mast-web will, which is a first for this repo.

## Open questions

1. **Typing at a halted session: send-and-say, or refuse?** Proposed: send, don't arm running, say it is queued (§2), because upstream built the inbox to queue for exactly this and the first turn after reset drains it. The case for refusing is that a queued message an operator has forgotten about will run the moment someone *else* resets the guardrail. Decide in PR 1, with the banner on screen.
2. **Should something warn us before the next gap?** Twice now the drift was found by a person reading upstream. A scheduled workflow that compares core-agent's `protocolVersion` with the mock's `wireProtocolVersion` and opens an issue when they differ would turn "the interval is the problem" into a control rather than a resolution. It is small, but it is not catch-up, so it is not in the seven PRs. Recommendation: add it, separately from this plan.
3. **Does a 1.19.0 refusal emit anything a client can wait on?** §2's last paragraph. Answered by PR 0 against the producer, not by reading.

## Rot condition

Mark this doc **executed** when v0.6.0 is tagged and all seven PRs are merged or explicitly deferred with a follow-up issue linked. **Mark, don't delete**, per v0.5's correction of the convention.

If the protocol has drifted again by the time v0.6 tags, record the new high-water mark here and let v0.7 carry it, exactly as v0.5 did. If it has drifted by *more than three minor versions*, that is a sign the interval is still the problem, and open question 2 stops being optional.
